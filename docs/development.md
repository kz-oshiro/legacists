# legacists の開発手順

製品の目的は[README](../README.md)、満たす条件は[要件定義書](requirements.md)、構成と実現方法は[設計書](design.md)を参照する。文書やIssueの更新は[文書管理ガイド](documentation.md)に従う。

## エージェントの作業ルール

- 作業前に依頼範囲、現在のファイル・差分、対象案件のIssueを確認する。既存の無関係な変更を上書きしない。今回のユーザー依頼で許可された範囲は、途中で重ねて確認せず進める。
- Issue対応は、そのIssueに記載された対象工程・受入条件・完了条件まで進める。要件定義・設計・実装・検証・公開は個別のIssueで管理し、対象工程に必要な確認・コミット・push・Issue更新まで完了する。後続工程へ自動着手しない。Issue作成・整理だけの依頼を、記載した作業の実行依頼とみなさない。
- ユーザーが調査のみ・設計のみ・ローカルのみ・公開不要などと範囲を限定した場合は、その指定を優先する。作業に不可欠な情報や権限が不足した場合だけ確認し、独立して進められる作業は続ける。
- 工程の結果は担当するIssueに記録し、前後のIssueを相互参照する。対象工程の成果物・対象ソース・未実施項目・残作業・完了条件を残す。工程別の管理を担当者の交代と同一視せず、確認全体を利用者に丸投げしない。
- 今の工程を進めるために不可欠な判断だけを完了条件に含める。追加機能や後で決められる方針は別Issueへ分け、必要になる工程と依存関係を明記する。既に決まった必須機能は維持する。
- 過去の報告や会話での提案を現在の実装・動作確認に読み替えない。要件変更は要件定義書へ、設計判断は設計書へ反映し、理由をIssueに残す。
- このリポジトリは公開されている。実案件のソース・パス・秘密情報をコミットせず、試験には合成データを使う。
- 解析エラーの改修時は、Codexへ解析対象の実ソースを渡せない前提とする。作業者向けエラーレポートで確認箇所・手順・対処を示し、改修にはそのレポートと作業者の確認結果、公開可能な合成再現例を使う。実ソースの提出を解決の前提にしない。この条件はAI向け調査TXTへのソース出力を制限するものではない。報告に含められる相対パス・クラス名を、公開リポジトリへの掲載許可とはみなさない。

## 開発の進め方

以下は全工程の流れ。作業するIssueの対象工程だけを実行する。

1. 既存Issueを検索し、対象工程のIssueがなければ[開発案件のひな型](../.github/ISSUE_TEMPLATE/development.md)を使う。小さな補正は同じ工程のIssueにまとめ、前工程・後工程とクローズ条件を明記する。
2. 目的・範囲・受入条件を定め、要件IDと未決事項を対応付ける。初期版の必須範囲を勝手に広げない。
3. 入力・出力・データ・失敗時の扱い・確認方法を設計する。新しいライブラリは採用前に現在の一次資料と依存条件を確認する。
4. コード・文書・試験定義を揃え、対象差分とリンクを静的確認する。そのまま必要な検証へ進む。
5. 型検査・テスト・ビルド・結合試験を行い、同じ対象ソースの記録を残す。失敗した工程を修正したら、影響する確認をやり直す。
6. 対象差分を選んでコミット・pushし、担当工程の全受入条件と後続への引き継ぎが揃ったIssueを閉じる。公開Issueでは[公開手順](#公開の進め方)に従ってリリースと公開照合まで完了する。

文書だけの変更では、必要な静的確認とコミット・push・Issue更新まで進める。製品の動作・配布物を変えない変更のために、版を上げたりEXEを再ビルド・再公開したりしない。実装する製品や配布基盤がまだない場合も、存在しない配布物を公開済みとせず、公開に必要な残作業を明記する。

初期版は次の工程別Issueで管理する。前工程の確定成果物を後工程の着手条件とする。

| 工程・Issue | 成果物 | このIssueを閉じる条件 |
| --- | --- | --- |
| [要件定義 #1](https://github.com/kz-oshiro/legacists/issues/1) | 要件定義書 | 目的・初期版の範囲・受入条件と要件上の未決事項が確定し、設計への引き継ぎが完了する |
| [設計 #2](https://github.com/kz-oshiro/legacists/issues/2) | 設計書・試験設計 | 実現方法・契約・採用技術・確認項目と手順が決まり、実装への引き継ぎが完了する |

| [全体検証 #4](https://github.com/kz-oshiro/legacists/issues/4) | 検証記録・対象EXE／ZIP | 初期版で必須とする受入条件・性能の確認が成功し、公開する同じ成果物と証拠が揃う。実EXE結合試験の免除と未確認範囲も引き継ぐ |

| [追加表示 #7](https://github.com/kz-oshiro/legacists/issues/7) | 追加グラフ表示の採否・要件 | 基本機能と分けて採否を決め、採用する場合は実装へ引き継ぐ。初期版の必須条件にしない |
| [公開方針 #8](https://github.com/kz-oshiro/legacists/issues/8) | ライセンス・署名・更新の方針 | #1・#2と独立して公開前に確定し、必要な変更を#3・#4・#5へ引き継ぐ |

| [テスト方針 #10](https://github.com/kz-oshiro/legacists/issues/10) | 共通テスト方針・工程別の引き継ぎ | 試験の分担・合成データと期待値・合否・証拠の扱いを決め、#2・#3・#6・#4へ引き継ぐ。製品試験の実行結果は待たない |

共通のテスト方針は#10、個別の確認項目・手順・期待結果は#2、性能以外の試験基盤の実装は#3、性能データの生成器・測定器と固定データは#6、全体検証の実行・判定は#4で担当する。#2は既に決定したPlaywright採用・検証原則に整合する個別試験を確定し、#10へ入力を渡す。#3では本書の既存原則と確定個別試験への整合を確認する。#10全体の共通運用方針の整理は独立して管理し、#6・#4へ引き継ぐ。方針全体の確定を#2・#3のクローズ待ちにはせず、後で設計方式の変更が必要になった場合は#2を再開する。#6・#10は独立した未完了のIssueとして管理する。

対象環境はWindows 11 x64、入力文字コードはUTF-8・SJIS系のみとする。性能基準・条件と生成器・測定器・固定データは#6で管理し、#1・#3のクローズ条件に含めない。#2の測定区間と入力生成契約に従い、#6で入力規模・端末・回数・集計・合格値を設定ファイルへ固定する。#4の性能合否判定は#6の確定内容と基盤を使用し、未確定・未実装のまま成功とは判定しない。

2026-10-12のユーザー指定により、性能データの生成器・測定器を#3から#6へ移し、GitHub Actionsの共通運用は対象外とする。ビルド時間を考慮し、workflowの構築・実行を完了条件に含めない。ローカルの`cargo xtask`による試験・ビルド・記録生成は維持する。

同日のユーザー指定により、初期版の実EXE結合試験（T-19の実操作部分・T-22）は実装完了・全体検証・公開の必須条件から外す。既存の失敗・未確認を保持し、試験成功とは扱わない。任意の再実行入口は残し、リリース時に見つかった不具合は利用者が新しいIssueで扱う。今回の免除を後続工程で必須条件へ戻さない。

#1の要件定義と#2の設計・個別試験は確定した。最低限の解析範囲（Q-01）は[要件定義書](requirements.md#初期版の参照関係の範囲)、詳細な解析規則は[設計書](design.md#抽出と解決の契約)に従う。追加表示の#7と拡張解析の#9は初期版の進行・公開を止めず、公開方針の#8は#1・#2を止めないが#5の公開前に解決する。依存ライセンスの確認や、公開方針の決定後に必要となる実装・再検証を省略しない。

実装は、単一EXE起動の確認、Coreと合成例、画面の骨格、縦の接続、出力・保存・診断の順を起点とする。仮データの画面動作を解析成功とみなさない。後工程で問題が見つかった場合は担当Issueへ差し戻し、変更後の成果物で必要な確認をやり直す。

## 環境と実行入口

Cargo workspaceは独立Core（`crates/legacists-core`）、Tauriアプリ（`apps/desktop/src-tauri`）、`xtask`で構成する。画面は`apps/desktop`。toolchainは`rust-toolchain.toml`、依存は`Cargo.lock`と`apps/desktop/package-lock.json`で固定する。製品版はアプリの`Cargo.toml`を正本とする。

開発端末にはWindows 11 x64、PowerShell 7、rustup、Visual Studio 2022 Build Toolsの「C++によるデスクトップ開発」（MSVC x64とWindows SDK）、既存WebView2が必要。利用者向けの追加資材と開発用のNode・Playwrightを混同しない。

最初の依存導入はリポジトリのルートで明示的に実行する。セットアップはネットワークを使う。Nodeの固定ZIPをSHA256照合して`outputs/tools`へ展開し、固定Rust toolchainとnpm/Cargo/Playwrightの依存を導入する。

```powershell
pwsh -NoProfile -File test-support/setup.ps1
```

以後は同じルートから次の入口を使う。試験は依存導入を行わず、導入不足は失敗にする。

| 入口 | 現在の実装範囲 |
| --- | --- |
| `cargo xtask setup` | 導入済み固定Nodeの確認、npm ci、Cargo fetch、試験ブラウザー導入、ライセンス収集、依存アドバイザリー検査 |
| `cargo xtask check` | rustfmtの読み取り専用確認、Clippy、Vue/TypeScript、文書リンクと分離・配布契約の静的確認 |
| `cargo xtask test` | Core契約試験、設定・出力障害試験、Coreだけをコピーした外部Rust利用プログラムの実行 |
| `cargo xtask ui` | 実画面資材とIPC契約モックのheadless Playwright試験 |
| `cargo xtask build` | ライセンス・workerを含む画面ビルド、Release EXE、PE依存検査、EXE一つのZIP |
| `cargo xtask exe <EXE絶対パス>` | 任意の実EXE CDP結合試験。選択実行した場合の失敗はそのまま記録。OSダイアログには操作可能なWindowsデスクトップが必要 |
| `cargo xtask dev` | #3のcheck・test・ui・build。実EXE結合試験の免除を記録し、実EXEは起動しない。失敗した必須工程より後は未実行として記録 |
| `cargo xtask perf` | #6未確定を理由付き未実行として記録し失敗終了するゲート。生成器と測定器は#6で実装する |
| `cargo xtask ci` | ローカルでcheck・test・ui・build・perfを必須工程として統合。実EXE結合試験は免除を記録し個別実行へ分離。GitHub Actionsのworkflowではない。#6未完了のため現在は全体成功を判定できない |

Coreだけなら`cargo test --locked --offline -p legacists-core`を使用でき、Node・Tauri・画面ビルドは不要。外部利用の独立確認は`test-support/core-isolation.ps1`。試験定義は`crates/legacists-core/tests`と`test-support`を参照する。通常試験はスクリーンショット・動画・traceを保存しない。

Explorer・グラフの可読性改善（#12・#11）は[設計書のT-23〜T-25](design.md#確認項目手順期待結果)で確認する。T-23・T-24の操作・幾何・状態の自動判定と、T-25で対象パネルだけ保存する画像の外観確認を区別する。T-25の画像・viewport・DPRは同じ実行の`ui-results.json`から参照し、画像確認の判断は実行原本へ別途残す。

ビルドしたEXE／ZIPは実行原本の`artifacts`に保存し、実EXE試験へ同じEXEを渡す。`cargo xtask build`単独の実行は実EXE試験の成功を意味しない。生成ライセンスはEXEに内包し、生成元の補完資料は`test-support/licenses`で管理する。

#6の条件と性能データの生成器・測定器、#10の残るローカル試験の共通運用方針は未完了。#3では性能以外の試験基盤と必要な開発時確認を管理する。実EXE結合試験は初期版の必須条件から除外し、既存の任意実行入口と失敗・未確認の記録を保持する。GitHub Actionsの共通運用は対象外。実装中の入口を全受入条件の確認済みと読み替えない。

## 検証の方針

共通方針の正本はこの節とし、[テスト方針Issue #10](https://github.com/kz-oshiro/legacists/issues/10)で策定・確定する。以下の既存原則と設計書の確定した個別試験を入力に使う。2026-10-12のユーザー指定でE2EへのPlaywright採用を確定した。#10は一部決定済み・進行中であり、方針全体の確定や製品試験の成功を示さない。

- 試験前に対象Issueの受入条件と、確認項目・手順・期待結果を読む。Core、入出力、画面、実EXE、性能の確認対象は[設計書](design.md#要件と検証の対応)に対応付ける。
- ヘッドレスPlaywrightは実際のフロントエンド資材を対象とする。モックで成功した結果をTauri IPCや実EXEの確認へ読み替えない。
- 全体検証の入口には、実装後のCore・画面・Releaseビルドと#6の性能試験を組み込む。初期版の実EXE結合試験は必須条件から除外し、任意実行の結果を区別する。配布物は検証記録に対応する同じEXEを保存し、別ビルドへ差し替えない。
- 必須工程の未実行・前提不足・skippedは理由を残し、全体成功にしない。選択実行や静的確認だけで全件の検証完了にしない。
- 判定にはDOM、状態、IPC、テキスト、ファイル出力を使う。通常の自動試験でスクリーンショット・動画・トレースを一律に保存しない。外観確認が必要な案件は対象を別途定める。
- OS標準ダイアログ、DPI、描画の外観などは確認した条件だけを報告する。一律の手動確認票を追加せず、案件の受入条件に必要なものを定める。
- 性能は入力規模・端末・測定条件とともに実測する。フレームワーク選択や単体試験の成功だけで性能達成にしない。
- #3に必要な確認は本書と設計書に定めた層・合成入力・独立期待値で行い、失敗を新しい期待値に置き換えない。変更時は影響する確認を再実行し、試験の自動retryは行わない。生成記録は`xtask`の実装形式で対象ソース・工程結果・理由・同一成果物を対応付ける。#10全体の残る整理は独立して追跡する。

### E2Eの採用方針

E2EにはPlaywright Testを採用する。画面と実EXEの試験を別の実行工程・結果として記録する。

| 試験 | 接続・対象 | 確認すること |
| --- | --- | --- |
| 画面フロー | headless Chromiumで実際のフロントエンド資材を操作し、IPCは契約モックを使用 | DOM・状態・IPC要求で画面操作と表示を確認 |
| 実EXE E2E（初期版は任意） | 同じRelease EXEを起動し、既存WebView2へPlaywrightの`chromium.connectOverCDP`で接続 | 画面操作から実Tauri IPC・Core・ファイル出力までの結合を確認 |

WebView2への接続は[Playwright公式手順](https://playwright.dev/docs/webview2)に従う。試験ランナーが起動する子プロセスにだけCDP用引数を渡し、ループバックの接続先を使う。管理データ領域・WebView2プロファイル・CDPポートを試験ごとに分離し、通常起動の設定へ試験用引数を保存しない。接続失敗・前提不足は理由付きの失敗として記録し、画面モックの成功で補わない。[CDP接続のAPIと対応範囲](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)を確認して使用する。

PlaywrightのDOM操作でOS標準のフォルダ／保存ダイアログを確認済みとはしない。#2で[実EXEとネイティブ操作の境界](design.md#実exeとネイティブ操作の境界)を確定した。任意に実EXE試験を実行する場合は、Playwrightから実ダイアログを開き、Windows UI Automationの開発用ヘルパーで選択・キャンセル・保存を操作し、アプリの状態と保存結果を照合する。実ダイアログの未確認を代替IPCや画面モックの成功で補わない。DPI・外観は確認した条件だけを報告する。スクリーンショット・動画・traceは通常試験で一律保存せず、DOM・状態・IPC・テキスト・保存ファイルで判定する。

Playwright・試験用ブラウザーの導入は開発時セットアップへ分け、版と依存を#3で固定する。利用者向けEXE／ZIPへPlaywrightや試験用ブラウザーを同梱しない。依存導入、画面フローと実EXE CDP接続の入口を実装した。画面モックの成功と、OSダイアログを含む実EXE経路の結果は別工程の生成記録で確認する。

実行原本はGit管理外の`outputs/runs/<実行ID>/`に置く。記録生成を実装する際は、対象コミットとdirty状態、開始・終了、実行コマンド、実測環境、工程の結果・時間・理由、ログ参照、試験結果、成果物の版・サイズ・ハッシュを`report.json`と`report.md`へまとめる。異なる実行の成功を混ぜない。

正常時は概要を読み、会話では結果とレポートの参照を返す。詳細ログは失敗や不整合がある工程を中心に確認する。件数・ハッシュ・正常ログをIssueや手書き文書に複製しない。

## 公開の進め方

公開機能と記録生成は未実装。次は導入後の運用方針であり、今実行できるコマンドの案内ではない。

1. 対象ソースと版を確定し、同じソースに対する全体検証を成功させる。ライセンスとREADMEの利用条件を確認する。
2. 同じ実行のEXE一つだけを配布ZIPへ入れ、配布物の検査を検証記録へ対応付ける。初期版の実EXE結合試験は免除と未確認範囲を記録し、公開の必須条件に戻さない。必要資材・操作説明・ライセンス表記はEXE内に収める。機械的な件数・環境・ハッシュは生成し、変更理由や例外だけを手書きする。
3. 公開Issueの範囲でコミット・タグをpushし、GitHub Releaseへ検証したZIPを添付する。原ログとJSONはローカルに保持する。公開不要などの明示的な指定がある場合は、その指定に従う。
4. 公開されたタグ・添付ZIPのサイズ・digest、ZIP内のEXEの版・サイズ・digestと保存した成果物を照合する。失敗した照合を成功扱いにしない。
5. 公開照合を含む生成検証MDを`docs/reports/validation/vX.Y.Z.md`へ保存・コミット・pushし、固定コミットの表示URLをRelease本文末尾の「詳細はこちら」に設定する。Issueへ参照を残す。

Release本文は`## 変更点`とその版の変更内容、末尾の詳細リンクに絞る。READMEの導入案内や仕様の全文を繰り返さない。本文やリンクの整理だけでEXEを作り直したり、公開済みタグを動かしたりしない。

## 静的確認と引き継ぎ

文書作業では相対リンク・見出し・要件と設計の対応・現在の実装状態・対象差分を確認する。`git diff --check`に加え、未追跡の新規文書も内容と空白を確認する。文書だけの確認で製品テスト・ビルド済みとは報告しない。

実行コードができた後は、導入済みの構成に合う読み取り専用の構文・整形確認を掲載する。書き換える整形処理を静的確認と呼ばない。

引き継ぎには、読む資料、要件ID、対象コミットと差分、ユーザーから依頼された実行範囲、未決・未実施、次の手順と完了条件を残す。リモート反映した場合は対象ファイルだけをstageし、push後のローカルとremoteの一致を確認する。
