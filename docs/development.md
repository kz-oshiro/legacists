# legacists の開発手順

製品の目的は[README](../README.md)、満たす条件は[要件定義書](requirements.md)、構成と実現方法は[設計書](design.md)を参照する。文書やIssueの更新は[文書管理ガイド](documentation.md)に従う。

## エージェントの作業ルール

- 作業前に依頼範囲、現在のファイル・差分、対象案件のIssueを確認する。既存の無関係な変更を上書きしない。今回のユーザー依頼で許可された範囲は、途中で重ねて確認せず進める。
- Issue対応は、要件定義・設計・実装・検証・ビルド・リリースまで一貫して完了する。必要な型検査・テスト・アプリ起動・GUI確認・コミット・push・タグ作成・GitHub Release公開・公開照合・Issue更新とクローズを通常の対応範囲に含め、工程ごとの追加依頼や承認を求めない。
- ユーザーが調査のみ・設計のみ・ローカルのみ・公開不要などと範囲を限定した場合は、その指定を優先する。作業に不可欠な情報や権限が不足した場合だけ確認し、独立して進められる作業は続ける。
- 要件・設計・実装・検証・公開の結果は区別して同じIssueに記録する。工程ごとに担当を分けることを前提とせず、必要な成果物・対象ソース・未実施項目・残作業・完了条件を残す。確認全体を利用者に丸投げしない。
- 過去の報告や会話での提案を現在の実装・動作確認に読み替えない。要件変更は要件定義書へ、設計判断は設計書へ反映し、理由をIssueに残す。
- このリポジトリは公開されている。実案件のソース・パス・秘密情報をコミットせず、試験には合成データを使う。
- 解析エラーの改修時は、Codexへ解析対象の実ソースを渡せない前提とする。作業者向けエラーレポートで確認箇所・手順・対処を示し、改修にはそのレポートと作業者の確認結果、公開可能な合成再現例を使う。実ソースの提出を解決の前提にしない。この条件はAI向け調査TXTへのソース出力を制限するものではない。報告に含められる相対パス・クラス名を、公開リポジトリへの掲載許可とはみなさない。

## 開発の進め方

1. 既存Issueを検索し、独立した案件がなければ[開発案件のひな型](../.github/ISSUE_TEMPLATE/development.md)を使う。小さな補正は既存案件にまとめる。
2. 目的・範囲・受入条件を定め、要件IDと未決事項を対応付ける。初期版の必須範囲を勝手に広げない。
3. 入力・出力・データ・失敗時の扱い・確認方法を設計する。新しいライブラリは採用前に現在の一次資料と依存条件を確認する。
4. コード・文書・試験定義を揃え、対象差分とリンクを静的確認する。そのまま必要な検証へ進む。
5. 型検査・テスト・ビルド・結合試験を行い、同じ対象ソースの記録を残す。失敗した工程を修正したら、影響する確認をやり直す。
6. 対象差分を選んでコミット・pushし、[公開手順](#公開の進め方)に従ってリリースと公開照合を完了する。全受入条件・公開記録・必要な引き継ぎが揃った案件を閉じる。範囲の限定や公開対象外の変更は、その理由をIssueへ記録する。

文書だけの変更では、必要な静的確認とコミット・push・Issue更新まで進める。製品の動作・配布物を変えない変更のために、版を上げたりEXEを再ビルド・再公開したりしない。実装する製品や配布基盤がまだない場合も、存在しない配布物を公開済みとせず、公開に必要な残作業を明記する。

初期開発は、次の順序案を起点に案件を切る。

| 段階 | 成果物 | 着手・完了条件 |
| --- | --- | --- |
| 導入条件の確認 | EXE一つだけのZIPと起動結果 | Q-02の対象CPU・起動条件を決め、既存WebView2を利用し、展開後とEXE単独の移動後に通常権限・追加インストールなしで起動を確認する |
| 最初の解析範囲 | 合成ソース、期待する関係、Coreの公開契約 | Q-01・Q-06から小さな対象を選び、根拠・未解決も判定できるようにする |
| 画面の骨格 | Explorer・グラフ・ソース表示 | 技術候補を評価する。仮データの動作を解析の成功と混同しない |
| 縦の接続 | 選択→Core解析→関係表示→根拠表示 | 同じ合成データでCore・IPC・画面の対応を確認する |
| 調査・診断機能の拡張 | 概要集約・出力選択・ソース付き調査TXT・作業者向けエラーレポート | R-04・R-06〜R-08の契約を決めて追加し、N-07の条件で解析エラーを切り分けられることを確認する |
| 配布の準備 | 全体検証、性能測定、配布物と公開記録 | 初期版の全受入条件、利用条件とライセンスを確定する |

導入確認・Core契約の検討・画面の試作は独立して進められる。上の順序案を工程の完了実績として扱わない。

## 環境と実行入口

現時点ではCargo workspace、フロントエンド設定、依存lockfile、`xtask`、CI、アプリは未作成。実行可能なセットアップ・テスト・ビルドのコマンドはまだない。

Rust/MSVC、Windows C++ Build Tools、フロントエンド用Node.jsとパッケージマネージャ、WebView2などの開発条件は、最初の構築時に版と導入方法をここへ記載する。利用者に必要な環境はREADMEへ記載し、開発環境と区別する。

共通入口を`cargo xtask`に集約する方針案を引き継ぐ。`setup`・`test`・`ui`・`exe`・`build`・`ci`・記録生成の役割を定義し、実装した入口だけを利用手順として掲載する。Vue等を採用する場合のフロントエンドビルド・worker同梱も含め、docs-searchのビルド方式をそのまま使えるとはみなさない。

依存導入はセットアップに分け、通常の試験で依存を黙って追加しない。lockfile・toolchain・実行コマンドをコードと一緒に管理し、製品版を複数の文書で手動管理しない。

## 検証の方針

- 試験前に対象Issueの受入条件と、確認項目・手順・期待結果を読む。Core、入出力、画面、実EXE、性能の確認対象は[設計書](design.md#要件と検証の対応)に対応付ける。
- ヘッドレスPlaywrightは実際のフロントエンド資材を対象とする。モックで成功した結果をTauri IPCや実EXEの確認へ読み替えない。
- 全体検証の入口には、実装後のCore・画面・Releaseビルド・実EXE結合試験を組み込む。配布物は結合試験で使った同じEXEを保存し、別ビルドへ差し替えない。
- 必須工程の未実行・前提不足・skippedは理由を残し、全体成功にしない。選択実行や静的確認だけで全件の検証完了にしない。
- 判定にはDOM、状態、IPC、テキスト、ファイル出力を使う。通常の自動試験でスクリーンショット・動画・トレースを一律に保存しない。外観確認が必要な案件は対象を別途定める。
- OS標準ダイアログ、DPI、描画の外観などは確認した条件だけを報告する。一律の手動確認票を追加せず、案件の受入条件に必要なものを定める。
- 性能は入力規模・端末・測定条件とともに実測する。フレームワーク選択や単体試験の成功だけで性能達成にしない。

実行原本はGit管理外の`outputs/runs/<実行ID>/`に置く。記録生成を実装する際は、対象コミットとdirty状態、開始・終了、実行コマンド、実測環境、工程の結果・時間・理由、ログ参照、試験結果、成果物の版・サイズ・ハッシュを`report.json`と`report.md`へまとめる。異なる実行の成功を混ぜない。

正常時は概要を読み、会話では結果とレポートの参照を返す。詳細ログは失敗や不整合がある工程を中心に確認する。件数・ハッシュ・正常ログをIssueや手書き文書に複製しない。

## 公開の進め方

公開機能と記録生成は未実装。次は導入後の運用方針であり、今実行できるコマンドの案内ではない。

1. 対象ソースと版を確定し、同じソースに対する全体検証を成功させる。ライセンスとREADMEの利用条件を確認する。
2. 同じ実行のEXE一つだけを配布ZIPへ入れ、展開後とEXE単独の移動後の結合試験を検証記録へ対応付ける。必要資材・操作説明・ライセンス表記はEXE内に収める。機械的な件数・環境・ハッシュは生成し、変更理由や例外だけを手書きする。
3. 通常のIssue対応に含めてコミット・タグをpushし、GitHub Releaseへ検証したZIPを添付する。原ログとJSONはローカルに保持する。公開不要などの明示的な指定がある場合は、その指定に従う。
4. 公開されたタグ・添付ZIPのサイズ・digest、ZIP内のEXEの版・サイズ・digestと保存した成果物を照合する。失敗した照合を成功扱いにしない。
5. 公開照合を含む生成検証MDを`docs/reports/validation/vX.Y.Z.md`へ保存・コミット・pushし、固定コミットの表示URLをRelease本文末尾の「詳細はこちら」に設定する。Issueへ参照を残す。

Release本文は`## 変更点`とその版の変更内容、末尾の詳細リンクに絞る。READMEの導入案内や仕様の全文を繰り返さない。本文やリンクの整理だけでEXEを作り直したり、公開済みタグを動かしたりしない。

## 静的確認と引き継ぎ

文書作業では相対リンク・見出し・要件と設計の対応・現在の実装状態・対象差分を確認する。`git diff --check`に加え、未追跡の新規文書も内容と空白を確認する。文書だけの確認で製品テスト・ビルド済みとは報告しない。

実行コードができた後は、導入済みの構成に合う読み取り専用の構文・整形確認を掲載する。書き換える整形処理を静的確認と呼ばない。

引き継ぎには、読む資料、要件ID、対象コミットと差分、ユーザーから依頼された実行範囲、未決・未実施、次の手順と完了条件を残す。リモート反映した場合は対象ファイルだけをstageし、push後のローカルとremoteの一致を確認する。
