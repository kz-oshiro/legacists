# legacists の文書管理

同じ事実の詳しい説明は一か所に置き、ほかはリンクでつなぐ。目標・設計・実装・検証済みの事実を区別する。

## 情報の置き場所

| 資料 | 読者と正本にする内容 |
| --- | --- |
| [README](../README.md) | 導入を検討する利用者。目的、実際にできること、必要環境、始め方、通信・保存・変更、制限、更新・問い合わせ |
| [要件定義書](requirements.md) | 利用者と開発者。目的、利用条件、機能・品質の要件、受入条件、対象外、未決事項 |
| [設計書](design.md) | 開発者。構成、依存方向、データ・API・画面・解析・出力の実現方法と要件への対応 |
| [開発手順](development.md) | 作業担当者。共通ルール、実際の環境と実行入口、検証・引き継ぎ・公開の手順 |
| [AGENTS.md](../AGENTS.md) | エージェント。タスク別に読む資料への短い入口 |
| [案件Issue](https://github.com/kz-oshiro/legacists/issues) | 1案件につき1 Issue。目的、判断、工程の現在地、成果物、受入条件と検証への参照、引き継ぎ |
| 案件から参照する試験設計 | 確認項目・手順・期待結果。初期はIssue内に記載し、大きくなれば再利用する試験設計として分離 |
| GitHub Release | 利用者。その版の変更点と公開検証MDへの固定リンク |
| 将来の公開検証MD | `docs/reports/validation/vX.Y.Z.md`。同じ実行の生成記録と公開照合結果 |
| ローカル実行原本 | `outputs/runs/<ID>/report.md`・`report.json`とログ・結果・成果物。Git管理外で保持 |

## READMEの管理

- 実装済みの機能と開発目標を分ける。配布前は配布物がないことを示し、実装後は実際の利用手順に更新する。
- 開発知識なしで導入判断できる説明にする。内部クレート、IPC、ライブラリ比較、開発の進捗は対応する文書やIssueへリンクする。
- 起動条件・配布方法・通信・保存・削除・制限・更新方法が変わる案件では、その機能と一緒にREADMEを更新する。
- 版・件数・性能値を手で繰り返し管理しない。最新配布版はRelease入口、確認環境や結果は生成検証記録を参照する。

## AGENTS.mdの管理

- ファイル名はルートの`AGENTS.md`とする。同じ目的の`agent.md`や`agents.md`を増やさない。
- 共通ルールとタスク別の資料リンクだけを短く置く。仕様、手順、試験ケース、長い禁止事項を複製しない。
- 詳細な作業ルールは開発手順、文書ルールはこのガイドを正本とする。正本の追加・移動・見出し変更時にリンクを更新する。
- 将来、特定の下位ディレクトリにだけ異なるルールが必要になった場合に限り、その範囲のAGENTS.mdを追加する。

## 要件・設計の更新

- 会話で確認した事項、整理時の案、未決事項を明示する。AIの提案を利用者が採用済みとみなさない。
- 何が必要かは要件定義書、どう実現するかは設計書へ書く。Issueには変更理由・対象ID・決定・受入条件との対応を残し、全文を複製しない。
- 現行の本文を直接更新し、改訂履歴はGitで管理する。独立した変更履歴、実装状況一覧、案件ごとの報告Markdownを増やさない。
- 要件IDを設計・試験・Issueから参照する。廃止したIDを別の意味で使い回さない。未決事項は解決した内容を本文へ反映する。
- 試験コマンド・対応版・保存先は実装と照合して更新する。未実装の入口や想定配置には、その状態を明記する。
- 日本語の管理文言は「フォルダ」に統一する。入力データ・引用・外部製品の文言は書き換えない。

## 案件Issueと引き継ぎ

形式の正本は[開発案件のひな型](../.github/ISSUE_TEMPLATE/development.md)。既存Issueを検索してから独立案件を作り、小さな補正は同じ案件にまとめる。最新の判断・状態は本文、途中の議論はコメントに残す。

| 工程 | 完了の意味 |
| --- | --- |
| 要件 | 目的・範囲・受入条件が決まっている |
| 設計 | 実装方法と確認項目・手順・期待結果が決まっている |
| 実装 | 必要なコード・文書・試験定義が揃っている |
| 検証 | 対象ソースと条件に対応する実行証拠がある |
| 公開 | 必要な場合に、タグ・配布物・公開記録を照合している |

対象コミット、実行ID、原本の場所、要件・試験・結果を対応付ける。ローカル原本は「ローカルのみ」と記載し、GitHubへのファイルリンクにしない。公開後は検証MDとReleaseを参照する。

次の担当はIssueと必要なコメント、現在のコード・差分を確認する。Issueはcloneに含まれないため、CLIでは次を使う。

```text
gh issue view <番号> --repo kz-oshiro/legacists --comments
```

Issue対応の依頼は、[作業ルール](development.md#エージェントの作業ルール)に従って要件定義からリリースまでを含む。工程ごとの追加承認や担当交代を前提にしない。今回のユーザー依頼に範囲の限定がある場合はそれを優先し、Issueや過去のコメントで限定を広げない。検証後に関係する実装が変わった場合は現在の検証を未完了に戻し、旧結果は旧ソースの証拠として保持する。

通常のIssue対応は、全受入条件とリリース・公開照合・必要な引き継ぎを完了してから閉じる。公開不要の指定や文書だけの変更では、公開を対象外とする理由と完了した範囲を本文へ残す。未実装・未測定の継続作業は開いた案件で管理する。`development`ラベルは運用開始時に用意し、ラベルがなくても一覧から案件を確認できるようにする。

## 検証記録とReleaseの管理

- 件数・時間・環境・ハッシュ・ログは機械生成する。手書きは変更理由、判断、例外、未確認の条件に絞る。
- 正常時は同じ実行の概要を読み、会話には結果とレポート参照を返す。詳細は失敗・不整合・ユーザーからの詳細依頼に応じて確認する。
- 不完全な記録、異なる実行の寄せ集め、部分成功を全体成功として扱わない。静的確認・自動試験・実EXE・OS固有の確認・性能測定を区別する。
- Release本文は`## 変更点`、その版の変更点、末尾の「詳細はこちら」リンクで構成する。リンク先は公開検証MDの固定コミットURLとする。導入方法はREADMEへ、技術表は検証MDへ置く。
- 版別のRelease本文をリポジトリへ複製しない。公開検証MDは当時の事実を保持し、訂正には理由を添える。文書改訂だけで製品版を上げない。

## 文書の静的確認

相対リンクと見出し、要件IDと設計・試験の対応、確定・候補・未実装の区別、公開できる内容、対象差分と空白を確認する。未追跡の新規ファイルも対象にする。Git管理外や未作成の場所を、存在する公開ファイルのようにリンクしない。

文書だけの作業では製品のテスト・ビルド・起動を行ったと扱わない。実行コードも変更した場合は、必要な検証と公開まで続ける。範囲の限定や前提不足で未実施の確認が残る場合は、確認方法・理由・完了条件を案件Issueへ残す。

次の実ファイルを基に、文書の分担、1案件1 Issue、工程別の引き継ぎ、機械生成記録、簡潔な成功報告、Release本文の管理を抽出した。

| [開発手順](https://github.com/kz-oshiro/docs-search/blob/94ac16fb85e07226806a089d059136c6b2189277/docs/development.md) | 作業範囲、工程分離、検証・公開の証拠を管理する |
| [文書作成ガイド](https://github.com/kz-oshiro/docs-search/blob/94ac16fb85e07226806a089d059136c6b2189277/docs/documentation.md) | 正本を分け、重複と手作業の結果転記を避ける |
| [開発案件テンプレート](https://github.com/kz-oshiro/docs-search/blob/94ac16fb85e07226806a089d059136c6b2189277/.github/ISSUE_TEMPLATE/development.md) | 案件の目的からリリースまで同じIssueで管理する |

docs-search固有の機能、版、件数、合格実績、Excel連携、実行コードは移植していない。`cargo xtask`などの共通入口・記録生成・実EXE試験は今後の構築方針として記載し、legacistsに実装済みとは扱わない。仕様の入口は要件定義書と設計書に置き換えた。

legacistsではユーザーの方針により、Issue対応を要件定義からリリースまで一貫して進める。docs-search由来の、実装とテスト・ビルド・公開を別依頼にする運用は引き継がない。
